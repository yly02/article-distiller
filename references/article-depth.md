# 深度文章编辑规范

## 文章目标

深度解读是把原文翻译好懂，不是另写一篇新文章。读者要能顺着原文的事实、演示、工具和限制看明白“它是什么、改了什么、怎么用”。章节顺序跟着原文走；需要补充官方定价、文档或演示时，只为把原文没写清的地方讲清楚，不借机改题。

## 写作引擎

全文只使用这一套引擎，不再另找“独特见解”当主线。

1. **标题**：高认知主体 + 材料支持的人话结果。产品稿写变化或规格，分析稿写冲突或划界，方法稿写具体对象能做出什么；不写“强到可怕”一类标题腔，也不在每个标题前硬加“深度解读”。
2. **一句导语 + 三条速览**：默认 3 条、合计仍短。第二条就是值得看的理由，不要写成“因为口径打架所以值得读”。三条的内容跟体裁走，见下表。
3. **开头跟体裁**：先判断原文是单产品、发布会、研究系统、论文临床、分析、方法、新闻还是商业动态，再用对应进入方式。同源功能套件仍算单产品，官方研究报告并进论文临床，不要另开技术前沿。不要把散文修辞套到产品稿，也不要把分析稿、方法稿写成产品能力清单，更不要把发布会或论文改成速查表。
4. **一节一项原文要点**：先一句话说清这一节，再拿出原文自己的框架、演示、步骤或例证，再告诉读者看哪里。单产品节点名演示；同源套件按任务难度拆；发布会先全景后逐台深挖；论文节写清样本、指标和哪些对比成立；分析节讲清原文划界；方法节写清闸门和对照。
5. **人话**：专名后面直接跟作用；原文的钉子句保留并翻译，不另发明评论主题。限制贴着它约束的那句话；句子短，少比喻。
6. **媒体贴着刚讲的那条能力**：改图、失败版和收紧版用前后对照；过程用视频，状态用静帧。没实际看见的画面、字幕和步骤不要编。外语媒体同时给中文图注和观看重点。
7. **要点讲完再写读者能带走的一步**。单产品写设置、写法和价格，套件再补权限/套餐；发布会写各设备门槛与官方口径；研究系统写评测和分工；论文写现在能说什么、不能外推什么；分析写判断落点和适用条件；方法写可执行顺序和不是生产文件的边界；商业动态写机制哪几件必须凑齐。演示、框架和步骤写够，安全和口径短写。
8. **发散只补官方附件、已看见的演示、参数、定价和原文自带的方法骨架**。不另写抒情评论，不抄对标站长提示词模板，不把对标站的会员栏、播客壳和相关阅读导流写进正文。

动笔前先列出原文要点清单，并标出体裁。清单上的要点默认都要进入正文；只有重复装饰、相关阅读配图或与要点无关的材料才能省略，并写下具体理由。

### 体裁落点

不要用产品三问去套所有文章。先选体裁，再写开头、速览和收束。对标站栏目名（产品发布、研究解读、深度解读、商业动态、AI实操、商业视觉实战、技术前沿）只帮助判断材料，不新增写作体裁。原文本身是速查手册才按索引写。

| 体裁 | 开头 | 速览三条 | 正文骨架 | 收束 |
| 单产品 / 发布 | 定义，再按原文能力往下讲 | 它是什么；读者多了哪一步；怎么用 | 一节一项能力，点名演示；同源套件按任务难度拆，不改成发布会 | 设置、写法、价格；套件补权限/套餐表 |
| 发布会 / 多产品 | 一条主线（算力、感知、云边界等）串起全部新品 | 这场会在落什么；几款怎么分工；购买前要看哪条门槛 | 先可切换全景卡，再逐台深挖；官方数字当官方数字 | 各设备门槛、发售与不能外推的实测 |
| 研究系统 | 定义 → 用户能做什么 → 首屏演示 | 发布了什么；它怎样工作；演示或评测证明了哪一步 | 机制 → 命名演示 → 数字证明什么 → 和现有系统分工 | 可能先改哪些场景，以及研究边界 |
| 论文 / 临床 | 先对齐标题口径和论文口径，再进入样本；官方研究报告先写官方定义 | 研究做了什么；样本和指标是什么；现在能说什么 | 样本路径 → 指标在测什么 → 哪些对比成立；原图带分母和时间，数字旁写不能证明什么 | 不能外推什么；后续试验只是后续，不是本文结果 |
| 分析 / 论述 | 旧预期 → 具体例子 → 原文要回答的问题 | 发生了什么；原文怎么划界；结论落在哪 | 原文框架、关键区分、例证；保留原文钉子句 | 谁在哪类条件下成立，什么时候不成立 |
| 方法 / 教程 / Skill | 失败模式 → 谁做了什么 → 方法压成一句 | 要解决什么失败；方法哪一步；读者能照着做什么 | 步骤、批准门、前后对照、控制权 | 可执行清单；概念稿不是生产文件 |
| 新闻 / 事件 | 谁、何时、何地、做了什么、结果怎样 | 发生了什么；为什么要紧；现在能判断什么 | 事件升级 → 证据 → 边界 | 已证实、仅声称、不能外推 |
| 商业动态 | 公司变大了还要快这类真实矛盾 | 解法是什么；机制哪一步；被它指到的人怎么说 | 短：矛盾 → 机制步骤 → 两边评价 → 同类类比 | 哪几件必须凑齐才叫机制；示意不是实测 |
| 危机散文 / 个人论述 | 跟原文进入方式，不改成说明书 | 它在说什么处境；关键转折是什么；读完留下哪一句 | 按原文论证走，不拆成产品能力 | 原文自己的收束，不另加行动清单 |

同一入口、多套难度不同的任务，仍选单产品，不要因为有三套界面就改成发布会。骨架是：共用入口 → 按难度拆任务 → 命名演示 → 权限/套餐表。官方实验室进展、内部评测报告并进论文/临床，不要另开技术前沿：先写官方自己的定义，原图带着分母和时间一起出现，数字旁边立刻写它不能证明什么；导语写材料支持的结果，不抄对标站抒情副题。推理时延、端到端墙钟、直播时延、吞吐倍率不是同一个“快”，必须拆开写；高配对基础款用决策表，价格写成运行成本。

章节标题用白话结果或具体问题，不用“背景、分析、影响、总结”。原文自带的阶梯、对照、控制权，优先做成可切换框架、对照表或流程，不要先写成文字墙。多产品全景用可切换设备卡；论文样本路径用流程；商业机制用短步骤条。自绘示意图必须写明按报道整理、不是实测数据。

## 默认读者与内容母稿

默认读者希望了解 AI 知识、资讯、产品和行业变化，甚至准备进入 AI 领域，但未必懂算法、工程和论文写法。按“聪明、好奇、非专业”校准：不居高临下，不省略关键逻辑，也不要求读者先掌握术语。

- 读者在前两屏知道这篇文章讲什么、为什么与自己有关。
- 首次出现且会阻碍目标读者理解的专有名词、缩写、指标和机制，先解释直观作用，再给专业名称、条件与边界。专有名词以官方或原始拼写作为唯一标识，不用编辑自创的中文说法替换。主标题、章节标题、图表标题和表头不追加翻译括注；存在稳定常用中文名且不说明会妨碍理解时，导语或正文首次出现必须写成 `原名（常用中文名）`，名词解释脚标不能替代这项正文括注。没有稳定译名、中文转述含义不确定或可能把描述误当正式名称时，直接保留原名，把身份、作用或通俗理解写进正文或名词解释。全文只说明一次。人名、品牌名、产品名、代码、模型编号和文件名不机械翻译；`AI`、`GPU`、`CPU`、`App`、`PDF`、`URL`、`Wi-Fi`、`ChatGPT` 等已进入大众语境的名称或缩写直接使用，也不生造音译。
- 读完后，读者能复述原文讲了什么、关键演示证明了哪一步、数字和工具怎么用；判断只在原文自己打架或必须划清边界时才写，不能压过原文要点。
- 文章作为博客、视频等后续内容的母稿，应保留一句话主旨、故事或机制主线、可独立提取的章节观点、适合转成画面的关系和有记忆点的结论；不能因此写成口播清单或卡片拼盘。

钉子判断只能来自原文自己给出的关键差异或取舍。删除产品名后仍适用于所有文章的句子，例如“AI 是双刃剑”“未来值得关注”，不能当主线。

## 成文语气

用语跟优秀白话解读学，不跟标题腔学：先用一句话说清这项能力，再点名原文演示，再写读者该看什么。句子短，少比喻，专名后面直接跟作用。不要把文章写成口径审判，也不要为了“独特见解”把原文重写成另一篇评论。原文是产品说明就写成说明文，原文是论述或危机文才跟着那种语气。

成品是一篇独立成立的文章，不是对研究过程的旁白。正文直接陈述事实、解释机制和给出判断，避免反复使用“原文说”“原博客强调”“这篇文章提到”“当前材料显示”等元叙述。需要标明来源时自然写出具体主体，例如“LTX 公布的测试”“Hugging Face 文件清单”“许可条款”；需要表达限制时写“官方尚未公布测试集”“没有独立复现”“现有数据不足以支持综合领先”，不要把证据状态写成割裂正文的审稿口令。

`原文声称`、`source_only` 等审计术语只保留在结构化研究账本和内部事实核查记录中，不进入 HTML 前端。逐字引文可以保留，但正文不能把“我们读了什么、又查了什么”当作叙事主线。编辑审校时单独检查并改写正文中的“原文/原博客/本文/当前材料/发布稿补充了”等过程话术；确有必要区分发布方与独立来源时，点名发布方或资料名称。来源区只保留读者需要的主材料名称、延伸阅读标题和自然来源说明，不提供可点开的详细链接，也不能展示审计说明、质量分数、抓取状态或对账结果。

### 标题与点击动机

标题不是原题翻译，也不是审计摘要。默认写法是「高认知主体 + 人话结果」：读者先认出是谁或什么产品，再看见这次改了什么。可以从真实材料中提炼动作、冲突、后果、具体数字或读者问题，但不能虚构，也不能抄对标站的极限词。

- 新闻或案例优先考虑“谁做了什么，结果怎样”或“读者最想追问的问题”。
- 产品、公告和研究突出读者能带走的变化或规格，不必机械套“主体 + 动作：解读范围”，也不用“全面升级”“强到可怕”替代具体结果。
- 标题可以比正文更有张力，但不能虚构主体、动作、数字或结果。未经证实的极限词改成问句、引语或明确边界，并在首屏解释。
- 标题承诺的变化、答案或结果必须在前两屏出现，不能靠标题吸引后把答案埋到文末。

### 先把事情讲明白

事件型文章先完成最基本的新闻叙事，再进入分析。首屏导语和第一节开头应尽快交代：谁、何时、何地、做了什么、结果怎样。信息未知时明确省略或说未知，不能拿证据边界代替事件本身。

- 第一段优先使用具体人物、时间、地点和动作，避免以“按材料描述”“这一区分很重要”“公开资料尚未披露”开场。
- 材料里若有能体现中心矛盾的真实小事、人物动作、案例或数字，可以先用一两个低理解门槛的例子建立处境，再在首屏内揭示事件主体、时间和机制。顺序是“具体例子或动作 -> 为什么值得在意 -> 谁做了什么”，不是先给抽象结论再补例子。不得虚构读者经历、补写现场细节，或把对比文章中的信息当作自己的素材。
- 第二段可以补充事件如何升级、关键转折或反常结果，给读者继续读的理由。
- 第三步再解释为什么、证据是否足够、机制如何运作和哪里仍未知。
- 限制贴着它约束的主张出现；不要在读者还不知道发生了什么时先摆一整块免责声明。

单产品、文档和发布说明没有人物事件时，先用一句话说清它是什么，再按原文能力往下讲。同源功能套件先讲共用入口，再按任务难度往下拆，不要一上来按三套界面列发布会。多产品发布会先给一条主线，再上全景卡，不要一上来按参数清单开场。研究系统可以紧接着让读者看见一次操作，再拆机制。论文、临床和官方研究报告先把标题概括和严格口径对齐，再写样本路径；官方数字带着分母和时间出现。分析稿用旧预期加一个具体例子进入，不要一上来做目录。方法稿用失败模式进入，但失败必须来自原文案例，不能编读者经历。商业动态先给真实矛盾，再拆机制，两边评价都写。机制解释文可以把参数先落到动作上，再给术语。原文本身是危机散文或长论述时，才跟那种进入方式，不要把文学开场套到产品稿。

### 好内容三要素

- **价值**：解决目标读者的一个明确问题，让人读完知道发生了什么、为什么重要或下一步怎么看。没有价值，排版和情绪都只是包装。
- **可读性**：用清楚结构、短段、人话和合适的表格或时间线降低理解成本。信息密度高不等于抽象名词多。
- **共鸣**：从真实的痛点、处境、选择和结果中找到“这和我有什么关系”。不编造个人经历，不强行煽情，也不拿泛化情绪代替证据。

审校顺序固定为“先价值，再可读性，后共鸣”。三者缺一时优先补最基础的一项，不用视觉形式掩盖内容缺口。

### 四层文章结构

“价值、可读性、共鸣”检查读者最终得到什么；下面四层检查文章靠什么实现：

- **灵魂｜立意与受众**：写给谁、原文要讲清什么，一句话就能复述。深度来自把原文能力、演示和限制讲明白，不来自另立评论主题或抽象词堆叠。
- **骨架｜结构与逻辑**：开头按体裁进入，中段按原文要点一节一项推进，结尾收回怎么用或还不能推出什么。演示详写，口径和安全短写；快速浏览标题也能抓住主线。
- **血肉｜素材与表达**：用事实、数据、案例和必要引文支撑判断；语言准确、流畅、简洁。故事、类比和画面感用来讲清真实材料，不编造情节。
- **颜值｜标题与细节**：标题负责真实地吸引点击，排版负责降低阅读阻力，引用、标点、数据和格式保持规范。颜值只能放大好内容，不能替代内容。

章节的 `tag` 是内部结构字段，只用于分类、兼容旧锚点和定位视觉元素。目录及正文小标题应直接展示自然、完整的标题，不在前面附加 `[风向]`、`[落地]`、`[主线]` 等编辑标签；这些标签重复标题含义，会让文章呈现为分析报告。

审校先后仍是灵魂、骨架、血肉、颜值。标题可以最先被读者看到，但不能最先决定文章写什么。

### 主题标签

主题标签服务于长期归档，不承担摘要或观点表达。通常保留 3-5 个稳定的大类名词，按“主体公司或机构、产品或模型家族、技术领域、应用领域、发布类型”选择。中文标签控制在 2-8 个汉字，纯英文标签不超过 12 个字符。禁止把中心判断、动作、数字、证据边界或营销话术写成标签；也不单独使用“AI、科技、行业”等无法有效归档的过宽词。发布方、作者、产品或平台名称只有在文章本身以该主体为分析对象时才进入标签；仅作为来源时不占标签位置。

### 四维写作标准

- **真实为底**：事实、发布方判断和编辑推论必须分清。趣味来自真实材料里的冲突、反差、机制和结果，不来自虚构人物、补写场景或夸张悬念。
- **讲透为骨**：不能停在“它很重要”或复述结论。至少回答“发生了什么、为什么会这样、它改变了什么、在什么条件下不成立”。关键数字要解释口径和意义，而不是只陈列。
- **人话为形**：先说直观意思，再给专业术语；优先使用具体主体和动作，少用抽象名词串联。需要读者反复回看的长句应拆开，但数字、条件和因果关系不能在拆句时丢失。
- **朋友感为声**：像一个懂行、诚实的朋友坐在读者旁边把事情说清楚。可以偶尔使用“你可以把它理解成”“真正需要留意的是”，但不要每段都称呼读者，不卖弄亲密感，也不使用教师训话、营销口号或居高临下的结论。

### 阅读节奏

- 先列出原文要点清单，再按清单分节。内部字段 `core_mechanism` 只用来一句话标出原文最需要讲清的那条变化或能力，不是另立的评论主题；章节跟着要点走，不要求每节都在证明这一句。
- `reader_tension` 只写目标读者在“它是什么、改了哪一步、怎么用”上容易卡住的地方。只能根据材料与任务语境概括，不代编内心戏，也不把口径冲突写成阅读主线。

- 解释型长文可让关键章节形成完整问答循环：标题替读者提出一个具体问题，正文前 1-2 句给出短答案，随后解释原因、证据和适用边界。读者不需要读到章节末尾才知道答案。
- 问题标题要能被本节材料直接回答，例如“为什么有些文字更容易被检出？”。不用“真相是什么”“这意味着什么”等脱离对象也成立的空问题，不连续使用同一种“到底/究竟/真的”句式制造紧张感。
- 问答循环是论证组织方式，不是要求正文连续写问句。给出一个问题后先回答，再继续展开；同一段不要叠加两个以上尚未回答的问题。
- 不要把所有章节统一做成问答模板。根据材料轮换开场动作：事件或场景负责建立处境，结果或数据负责制造信息差，例子负责降低理解成本，冲突或反常现象负责提出问题，明确判断负责推进论证。相邻两节若开场动作和内部结构都相同，至少改写一节。
- 每节只承担一个主要任务，优先对应原文一项能力或判断。先让具体证据、动作、数字或演示出现，再解释它意味着什么。产品能力节把命名演示写进正文：画面改了什么、什么没动。形容词不能代替证明，背景只有在改变当前判断时才获得篇幅。
- `sections[].content` 较长时拆成 2-4 个短段。每个段落只承担一个动作：给判断、摆事实、解释原因或收边界。短句与中等长度句交替，避免整段只有同一节拍。
- 在论证转折较大的章节末尾，可用 `sections[].transition_hook` 写一句读者自然会追问的问题，把阅读动作交给下一节。它属于次级阅读提示，视觉上用竖线、小于正文 `h2` 的字号和次级文字色，不能呈现为第二个章节标题。全文通常使用 3-5 次，不要求每节都有；下一节开头必须直接回答或展开这个问题，最后一节通常留空。
- `transition_hook` 只能追问现有材料里的机制、证据、边界或行动含义。下一节标题可以把同一疑问压缩成更便于扫描的问法，但不能逐字复制；正文必须立即回答。连续两节使用同一种“那么……到底……”句式时应改写或删减。
- 类比只用于降低理解成本，而且必须准确映射机制。材料没有真实案例时，可以使用明确标为“类比”的生活经验，不能把它包装成真实事件。
- 少用“值得注意的是、综上所述、总体来看、从某种意义上、不难发现、毋庸置疑”等报告套话。删除这些词后句子仍成立时，直接删除。
- “不是……而是……”适合纠正一个真正的误解，但不能成为全篇统一句式。连续使用会让文章听起来像结论海报，而不是自然解释。
- 专业名词第一次出现在 HTML 正文时，词后紧跟小型 `i` 脚标。桌面端悬停或键盘聚焦时，在脚标附近浮现术语、准确定义和通俗理解，移开或失焦即消失；点击或触屏轻点可固定展开，再点空白处或按 Escape 关闭。固定展开只固定开关状态，浮层仍锚定脚标并随正文滚动，不得固定在浏览器视口。术语解释不再复制到右侧栏。之后直接使用，不要反复加脚标或定义。
- 知识背景只在当前论证需要时出现，先出现问题或现象，再补刚好够用的解释。没有改变机制理解的历史、文化或哲学参照应删除。
- 合理异议先按最强版本陈述，并说明它在什么条件下成立，再补充材料带来的新条件。不要虚构“你可能会觉得”作为容易反驳的靶子。
- 长短句可以自然变化，关键处允许一个独立短句；但不把粗口、网络梗、连续问号、省略号、故意病句、虚假犹豫或虚构第一人称体验当作活人感。

### 人味检查

人味来自选择和呼吸，不来自口癖。卡兹克方法只借用功能：先确认有趣、有新知、有材料里的真实连接；多个结果按“基础现象 -> 更明显差异 -> 最能改变判断”递进；背景知识从当前例子长出来，不为升华另起科普。

- 全文可以有一句钉子判断，但必须是原文自己给出的关键差异，用读者能复述的话说出来；只出现一两次，后面用演示兑现，不要另起评论主题。
- 提出判断前，先把合理的另一种选择或失败原因讲完整。
- 成稿后查：多个中心、段段金句、匀速排比、替读者说蠢话再纠正、假故事、假脆弱、强行升维。删仪式化表达，保留一两句真正有力的话。
- 不吸收任何作者的口癖、粗口、连续省略号或“我亲自试过”。没有第一手经历，就用编辑视角写。

其余语气、标题、章节和验收以本文为准，不必再读单独的人味或对标长文，除非要核对卡兹克边界或对标站“不能抄什么”。

### 可视化叙事

可视化不是装饰。出现三项以上对比、明确时间顺序、多步骤机制、因果分支或数字关系时，优先考虑表格、时间线、流程图、统计卡或互动对比；一句话已经能说清的内容不要硬做卡片。原文的能力阶梯做成 stepper，单据对任务、稳定项对变量、谁能决定什么做成对照表或控制权表；静帧给状态，视频给两帧之间的过程。视觉组件必须紧跟它解释的段落，并让读者不看正文也能理解标题、对象和结论边界。

## 研究账本

`research_ledger.claims` 保存原子主张及证据状态。论文或报告确有实验时，`research_ledger.experiments` 还需记录问题、环境、样本、模型、指标、结果、对照、人工条件、限制和关联 `claim_ids`。材料确有具体事件链时才建立 `research_ledger.cases`。

高优先级实验和案例必须进入成稿，除非在 `editorial_coverage.omitted_claims` 中说明与原文要点无关或证据不足。未知信息写“未知”或“无明确对照”，不能自行补齐。

## 成稿组件

- `narrative_plan`：内部阅读契约。公开文章按原文要点清单推进；这些字段只帮助写作对齐，不渲染到前台。
- `narrative_plan.source_points`：动笔前列出的原文要点清单，每条对应后文一节或明确的省略理由。
- `narrative_plan.target_reader`：本篇具体写给哪类 AI 初学者，以及他们已有和缺少的认知。
- `narrative_plan.reader_tension`：读者在“它是什么、改了哪一步、怎么用”上容易卡住的地方，不编造心理活动。
- `narrative_plan.reader_takeaway`：读者看完能复述的原文要点、关键演示和用法。
- `narrative_plan.core_mechanism`：原文最需要讲清的那条变化或能力，用一句话说它怎样起作用；不是另写的评论主题。
- `narrative_plan.distinctive_insight`：原文自己给出的关键判断或能力差异，不能是通用口号，也不能是编辑另写的抒情评论。
- `narrative_plan.opening_anchor`：产品稿可以就是定义句；新闻或案例用来自材料的真实小事、动作或数字。没有合适锚点时写“直接陈述事实”。
- `narrative_plan.reader_stake`：这件事具体影响目标读者哪一种判断、选择、成本或机会，不能泛写“与每个人有关”。
- `narrative_plan.resonance_basis`：用来建立共鸣的真实处境、冲突、取舍或后果，以及它对应的材料依据。
- `narrative_plan.stance`：编辑最终站在哪个可辩护判断上、依据是什么、什么条件会使判断改变。产品稿的立场通常是“把原文能力讲清楚”，不要另立审判。
- `narrative_plan.title_contract`：标题的高认知主体、唯一人话结果、读者承诺和证据边界。
- `narrative_plan.opening_sequence`：按体裁完成首屏。单产品用定义、变化、用法；同源套件用共用入口、任务阶梯、权限边界；发布会用主线、全景分工、门槛；研究系统用定义、一次操作、机制；论文和官方研究报告用官方定义、原图口径、样本；分析用旧预期、具体例子、原文问题；方法用失败模式、案例动作、方法一句；商业动态用矛盾、机制、两边评价；新闻才用具体场面进入。
- `narrative_plan.chapter_system`：先选 `product|lineup|research|paper|analysis|method|event|business|investigation|explainer`。单产品按能力，同源套件仍选 `product`，发布会先全景后深挖，研究系统按机制-演示-评测，论文和官方研究报告选 `paper` 并按样本-指标-对比，分析按划界，方法按步骤闸门，商业动态按短机制。每节登记它覆盖的原文要点、演示/框架/步骤和承接。
- `quick_scan`：标题后的“一分钟速览”，严格 3 条、每条 35-60 字、总计不超过 180 字。单产品回答“它是什么 / 多了哪一步 / 怎么用”；同源套件第二条写清共用入口多了哪类任务；发布会回答“这场会在落什么 / 几款怎么分工 / 门槛在哪”；研究系统回答“发布了什么 / 怎样工作 / 证明了哪一步”；论文和官方研究报告回答“研究做了什么 / 样本和指标是什么 / 现在能说什么”，不要把多口径速度数字捏成一句“很快”；分析回答“发生了什么 / 原文怎么划界 / 结论落在哪”；方法回答“要解决什么失败 / 方法哪一步 / 读者能照着做什么”；商业动态回答“解法是什么 / 机制哪一步 / 被指到的人怎么说”。原来单独写的推荐理由并进第二条，不另开首屏段落，也不要把口径冲突、审计状态或孤立数字当主句。它只先给三条结论，不承担目录导航。
- 目录：完整文章唯一的章节导航，显示完整标题并跳转到对应段落。“一分钟速览”只保留三条结论，不生成章节摘要、跳转入口或第二套导航；也不要生成放射状思维导图，避免长标题被截断并与目录重复。
- `sections`：至少 3 个章节，每段有唯一 ASCII `id`；关键解释章节可使用具体问题标题，并让 `content` 的前 1-2 句直接回答，其他章节使用能准确标记论证进度的具体标题。可选 `transition_hook` 只承担章节间的阅读牵引，不承载新的事实或结论。
- `experiment_ledger`：实验问题、条件、样本、指标、结果、对照和限制；用 `after_section_id` 紧跟相关论证。
- `case_stories`：至少三步有证据的事件链、结果和边界；用 `source_mode` 区分证据重建与逐字引述。
- `visuals`：只把已有关系转成表格、流程、时间线、数据图或交互组件，不生成新事实。`rank_bars` 用于同一单位、同一口径下多个对象的数值排序，分组内按绝对值降序，正负参数分开显示；`metric_bars` 用于同一批对象存在两组以上不同含义的数值指标：先切换读者问题，再在每个对象内部比较主方案和对照，保留原值、单位、优势方向和证据边界，条长不得跨指标比较。`delta_table` 用于同一指标有明确版本、时间或调整前后关系的变化；`status_matrix` 用于多个对象跨多个固定维度的支持覆盖状态；`decision_table` 用于条件决定结果并对应可执行行动，来源规则与编辑建议必须分开。`funnel_flow` 只用于真实资格关口逐级淘汰对象，普通顺序仍用 `flow`。`interactive_compare` 仅用于同一组候选在不同模式下产生不同结果的机制；`scenario_calculator` 仅用于来源图表已有可比较对象、可靠基数和清楚计算关系的场景，把原图重构为对象切换、假设滑块和实时结果。交互组件都必须提供边界说明，并在无脚本时保留完整静态内容。
- 每个视觉先写清 `reader_question`，再按材料中的真实关系选择表达。架构层级、能力分层和上下游依赖用 `layer_stack`；它展示2至7层摘要，并允许展开职责和组成。流程、时间和平级比较不得伪装成层级。同一章节通常只保留一个主视觉，来源图、音频或视频可以补充证据；连续三个相同组件或多个组件复述同一事实都应重做。
- 互动的判断标准不是“页面看起来更丰富”，而是读者操作后能亲自观察到变量、条件、阶段或结论发生变化。3至7个解释较长的流程阶段可用 `flow.stepper`，3至8个有独立解释的时间节点可用 `timeline.scrubber`；简短流程与日期清单保持静态。所有互动必须有无脚本的完整静态降级，不能让关键事实只存在于隐藏状态。
- `number_stories`：作为高优先级数字主张的审计账本保留完整口径，但不默认逐条展示。公开数字默认 `display_variant=compact`；只有数字本身是文章核心结论、必须同时看统计对象、时间、对照和变化时才展开。辅助背景数字即使重要也保持紧凑；正文或其他视觉已说清时设为 `suppress_visual=true`。不能把内部审计字段直接铺成长图或数据表。推理时延、墙钟、直播时延和吞吐倍率必须分条登记，不能合成一个“快”。官方研究报告的主数字必须带着分母、时间和“不能证明什么”。
- 数据视觉采用可复用的语义颜色：主方案绿色、对照系统蓝色、限制说明琥珀色，并让图例、横条、数值强调保持一致；不要每个指标换一套颜色，也不要只用同一蓝色的明暗变化区分所有角色。状态矩阵的颜色必须对应稳定状态词，变化表和决策表的颜色必须对应明确方向或风险；普通表格只使用轻量表头、隔行底色和交互反馈，避免无业务含义的彩虹分列。
- `source_media`：从原文或已抓取附件的媒体注册表中选择真实图片或视频，用 `after_section_id` 放在其支持的段落之后。素材可展示界面、案例、演示过程或官方图表，但不能单独证明性能结论；装饰图和品牌横幅应舍弃。正文图片按原始比例直接插入，不使用固定高度容器、黑色补边或装饰边框；视频可保留播放器所需的黑色背景。正文可见图注只说明图中内容，不追加“素材来源”“来源素材”或“出处”链接；上游来源保留在数据层和页末证据图库。
- `fact_check` 与 `editorial_coverage`：在 JSON 中逐项保留证据强度和研究覆盖；发布页只把 `fact_check` 渲染成默认折叠的“资料与边界”状态摘要和来源链接。

文章补充注释使用固定语义，不以同一种粗体、斜体或左边线混用：`analogies` 显示为带“类比”小标签的理解辅助；`concept_explainers` 显示为“名词解释”，内部区分术语、定义和“通俗理解”；必要的 `archive_original` 显示为“原文引文”，同一编号旁注内分别标明“英文原句”和“中文释义”。小标签只说明用途，不写审计状态。

HTML 中目录、`concept_explainers` 与必要的 `archive_original` 属于阅读辅助，不占正文流：宽屏左侧固定目录并随滚动高亮章节；术语第一次出现在正文时紧跟 `i` 脚标，桌面悬停即时浮出解释，点击或触屏轻点可以固定展开，不再生成右侧术语栏。只有确有必要的完整原文引文才使用右侧栏，正文对应位置保留“相关引文 [n]”。类比继续留在正文。

`archive_original` 默认留空，全文最多 2 条。只有以下情况才值得保留：原句措辞本身是论证对象；翻译或转述会损失关键限定；争议性主张需要读者核对发布者究竟怎样说。正文已经讲清的普通事实、数字和结论，或已经能从来源图表直接核对的信息，不得为了丰富旁注再次摘引。

`claim_ids`、实验 id 和证据状态只服务于审计与覆盖检查，不能作为面向读者的标签。HTML 可以把完整实验条件默认折叠，但摘要标题要能说明结论，展开后仍须保留样本、指标、对照和限制。行动卡与带走清单若内容重复，只保留更适合当前文章的一种。

## 叙事门禁

- `distilled_title` 必须有真实点击动机，并能在材料中找到所承诺的人物、动作、冲突或结果；营销表达不能制造材料外事实。
- 事件型文章的 `one_liner` 和第一节开头必须优先交代谁、何时、何地、做了什么、结果怎样；产品稿的 `one_liner` 先定义它是什么，细节放到第一节。`one_liner` 控制在约 40-70 字；不要在标题下再放 `recommendation_reason`，`quick_scan` 第二条写读者多了哪一步。
- 开头采用例子先行时，例子必须来自研究账本或已读取证据，并在首屏内完成“例子 -> 背景矛盾 -> 事件主体与机制”的揭示；移到开头的例子不得在后文再次成组复述。
- 主编按“价值、可读性、共鸣”检查开头和全文，先确认读者看懂并有收获，再优化节奏和情绪连接。
- 主编再按“灵魂、骨架、血肉、颜值”逐层验收：主旨是否唯一、结构是否闭环、素材表达是否站得住、标题排版是否放大而非掩盖内容。
- 主编必须以聪明的 AI 初学者视角通读：不查外部资料能否看懂首次术语，能否复述原文讲了什么、关键演示证明了哪一步、怎么用；后续改成博客或视频时是否有清楚主线可提取。
- 每节必须覆盖清单上的一项原文要点，不能只换标题重复结论，也不能用编辑评论挤掉演示。
- 主编检查逐节任务和结构变化：相邻章节不应连续使用同一种开场动作，三个以上章节不应共享完全相同的“提问、回答、举证、限制”骨架。结构变化必须服从材料，不能为求花样硬塞故事。
- 每节都要能回答“读者为什么现在要知道这一点”；较长正文必须有自然分段，不能把结论、证据、机制和限制压成一堵文字墙。
- 主编必须检查“问题标题 → 开篇短答案 → 证据展开”是否闭合：问题不能超出材料，答案不能延迟或答非所问，证据和边界不能被口语化删掉。
- 主编必须逐一检查非空 `transition_hook`：它是否承接本节、是否由下一节立即回答、是否与下一标题逐字重复、是否与其他钩子句式雷同。无真实问题可追问时宁可留空，不为达到数量硬加反问。
- 主编必须检查报告套话、术语堆叠、过长句和单一句式反复，并在修订稿中实际改写；朋友感不能以降低证据精度为代价。
- 主编必须执行“过度完美检查”：段段金句、匀速句长、固定连接词、连续反转、替读者发问再纠正、假脆弱、假故事和强行升华都应回到具体事实与自然表达。保留一两处真正有力的句子即可。
- 实验数字必须连同样本、指标、对照和人工条件出现。
- 案例重建必须明示不是逐字记录；没有引文不得加引号或虚构对话。
- 限制和反例应放在它们约束的结论附近，而不是统一塞到免责声明。
- 结尾明确回答开头问题，并区分“材料已证明”“原文声称”“尚不能外推”。
- 最后做一次脱离标题、摘要、提纲和来源说明的冷读。只读正文也应能回答“原文讲了什么、关键演示证明了哪一步、读者怎么用”。再做删除测试：删掉任一段不影响理解，说明该段未完成独立任务；把最后两段分别删掉试读，删后更有力就提前结束。

## 发布验收

- 标题下只有一句短 `one_liner`，不放 `recommendation_reason`；一分钟速览三条跟体裁走，默认仍是 3 条。文末不用打勾清单一一复述结论，`takeaway_list` 不渲染。
- 页末来源区只显示来源名称，不提供可点开的详细链接。
- 审计字段、claim id、质量报告、抓取/媒体对账状态、研究账本、`fact_check` 和 `source_notes` 不得进入 HTML。
- 所有 high 主张、实验和案例已覆盖或有具体舍弃理由。
- 所有 `claim_ids` 与 `after_section_id` 均真实存在。
- 实验和案例各渲染一次，位置紧随相关段落。
- 正文原始图片和视频均已登记、无重复、锚点有效；正文各插入一次，证据图库按 URL 各登记一次。视频正文保留 controls 和可用 poster。
- 正文媒体图注没有“素材来源、来源素材、出处”等尾注；来源 URL 仍完整保留在 JSON 与页末证据图库。
- 正文图片保持原始比例，没有固定最大高度、黑色补边、播放器背景或装饰边框；视频样式与图片样式分离。
- high metric 均有完整数字叙事，主数字与分母、时间、范围、对照或变化、边界和来源一并出现；不完整数字没有被做成大数字卡。
- 原始证据图库默认折叠，只包含已登记且有论证价值的图表、截图或演示，并能打开原始文件与来源页面。
- 宽屏目录位于正文左侧且不改变正文宽度；目录和原文引文栏展开后，点击页面空白处或按 Escape 必须自动收起，关闭后保留紧凑入口。术语浮层不得越出正文栏或遮挡固定导航，点击固定后滚动页面时必须随对应脚标移动。必要的原文引文栏位于右侧。窄屏点击术语脚标可固定展开浮层，点击引文编号可打开并定位引文栏，不遮挡或挤压正文。
- HTML 的目录及正文小标题均不显示内部 `tag`，也不存在与 tag 同值的前置方括号标签。
- 主题标签数量为 3-5 个，能够覆盖中心判断、关键机制和现实后果；不存在仅因来源身份加入的发布方名称，也不以宽泛行业词凑数。
- 主标题、章节标题、图表标题和表头中的专有名词保留官方或原始拼写，没有翻译括注，也没有用编辑自创的中文别称替代；导语或正文中确实影响理解且存在稳定常用译名的陌生名称，首次出现必须采用 `原名（常用中文名）`，不能只做名词解释脚标；没有稳定译名时通过正文或名词解释说明作用；同名后文不重复括注。
- `transition_hook` 的字号、颜色和字重明显弱于相邻 `h2`，但仍通过竖线和半粗体保持可识别性；不得与章节标题形成同级竞争。
- 来源声明、证据状态、链接和结论边界统一收进页末默认折叠的“资料与边界”；正文入口不再额外展示核查说明，也不重复完整核查账本。
- 客户可见产物不显示生成器名称、功能介绍、输出格式说明或通用免责声明；页尾若无业务品牌或真实内容需求，直接结束，不添加技术署名页脚。
- 原始材料的标题链接、作者和发布日期属于溯源署名，不放在标题与导语之间；HTML 统一在文章最末尾以次级小字展示，不与“资料与边界”的证据摘要混写。
- 无空段、占位符、重复段、原始 HTML 泄漏或移动端横向溢出。
- 机制互动无需 JavaScript 也能看到默认状态；切换按钮可键盘访问、状态有 `aria-pressed`，移动端不横向溢出。
- 证据情景卡至少有两个可切换对象、来源指标、合法滑块、计算基数、公式说明和来源媒体；来源数值、近似图表读数与读者假设在视觉和文案上明确区分。无 JavaScript 时仍显示默认情景，移动端按钮、指标和滑块不溢出。
- 返回顶部控件具有真实的文章顶部锚点、可访问名称和键盘可用性；点击能回到标题区，JavaScript 仅增强平滑滚动，不作为唯一实现。
